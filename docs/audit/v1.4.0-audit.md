# v1.4.0 audit — main branch baseline

Audit date: 2026-10-30  
Audited ref: `main` at `7a6d5ad15f044e80a2522125660b080a8125ee5f`  
Scope: source/documentation inspection only. No implementation or local test run was performed before this audit.

## Executive summary

The previous audit's central finding needs correction: current main already contains three OCR model dependencies and the engine accepts a language parameter. However, the UI language selection is **not connected end-to-end**: the selected value is stored in the batch store and passed in processor options, but `src/features/pipeline/processPdf.ts` calls `ocrPdf(file, callback)` without forwarding `options.ocrLanguage`. The engine therefore uses its default `eng`. The select is visually present but functionally a placeholder at the point of recognition.

Mixed text/scanned PDFs are also a confirmed gap: OCR is invoked only when the entire PDF is classified `image-only`.

## 3. OCR implementation audit

### Language selector and pipeline

- `src/app/App.tsx`: state is `useState<OcrLanguage>('eng')`; selector values are `eng`, `deu`, `hin`. It passes the selected value to `ResultsTable` and `store.requestOcr(id, language)`.
- `src/types/batch.ts`: `OcrLanguage = 'eng' | 'deu' | 'hin'`; processor options include optional `ocrLanguage`.
- `src/features/batch/batchStore.ts`: `requestOcr(id, language)` stores the choice and passes it as `ocrLanguage` to the processor.
- `src/features/pipeline/processPdf.ts`: confirmed defect — calls `ocrPdf(file, progressCallback)` and drops `options.ocrLanguage`.
- `src/features/ocr/ocrEngine.ts`: accepts `language = 'eng'`, verifies `manifest.languages.includes(language)`, and calls `createWorker(language, 1, options)`.

Conclusion: **VERIFIED GAP** — UI state and batch state are wired, but the last pipeline handoff is missing. Tesseract always receives its default English language for the current processPdf path.

### Assets and same-origin behavior

- `scripts/prepare-ocr-assets.mjs` allowlists `eng`, `deu`, `hin`, copies worker/core/model files to `public/ocr/`, and writes a manifest. It currently supports local `ocr-data/` overrides and npm package files.
- `src/features/ocr/ocrManifest.ts`: `ocrAssetBase()` uses `import.meta.env.BASE_URL + 'ocr'`; manifest fetched from that same-origin path.
- `src/features/ocr/ocrEngine.ts`: workerPath, corePath and langPath all derive from `ocrAssetBase()`; `workerBlobURL: false`; `cacheMethod: 'none'`.
- `index.html`: CSP includes `connect-src 'self'`, `worker-src 'self' blob:`, and `script-src 'self' 'wasm-unsafe-eval'`. No external OCR origin is configured.
- The package-lock pins `@tesseract.js-data/eng`, `deu`, and `hin` at 1.0.0. `docs/THIRD-PARTY-LICENSES.md` lists those package names as MIT.

Source-level conclusion: **VERIFIED** same-origin asset path design and CSP compatibility. Runtime Network-tab behavior: **NOT VERIFIED**.

### Worker, canvas, progress, cancellation and errors

- Worker is created per `ocrPdf()` call and terminated in its outer `finally`: VERIFIED.
- PDF is destroyed in the same `finally`: VERIFIED.
- Canvas dimensions are reset after successful recognition: VERIFIED on success path only.
- Canvas release on render/recognition failure: **VERIFIED GAP** — canvas cleanup is not in a per-page `finally`.
- Worker reuse/cache: no worker cache; worker is created and terminated for each OCR run. This is safe from shared-worker cross-language state but incurs startup cost.
- Progress: logger maps Tesseract recognition progress to current page; rendering emits per-page progress; pipeline maps it into the batch progress range. VERIFIED in source.
- Cancellation: no cancellation signal or cancel action was verified. **VERIFIED GAP** for requested mid-run cancellation.
- Missing manifest / unsupported language: engine throws `OCR_UNAVAILABLE`; manifest fetch errors return null. VERIFIED basic failure detection.
- Missing/corrupt individual traineddata, out-of-memory and user-facing retry: **UNVERIFIED**; no verified language-specific recovery flow/test.
- Limits: 20 OCR pages (`OCR_MAX_PAGES`); 24,000,000 canvas pixels (`OCR_MAX_PIXELS`); render scale up to 3 (~216 dpi); global PDF validation limits 25 MiB and 100 pages. No explicit OCR wall-clock timeout was found in `src/config/limits.ts`.
- Mixed text/scanned PDFs: **VERIFIED GAP** — pipeline OCR branch checks only `raw.kind === 'image-only'`; it does not OCR individual image-only pages in a mixed document.

## 4. OCR language vs invoice locale

The concepts and state are separate in source:

- Invoice locale: `LocaleCode` from `src/config/locales.ts`; defaults to `en-IN`; controls date and numeric interpretation and reprocessing.
- OCR language: `OcrLanguage` in `src/types/batch.ts`; defaults to `eng`; should control Tesseract recognition only.

The selectors are currently in one panel headed “Number and date format”; the OCR selector has no separate heading/helper. The CSS lays out each field as label/copy plus select, but the JSX nests both in one group. This is a verified UI semantics/layout gap. Do not derive OCR language from invoice locale or change parsing contracts.

## 7. Packaging gate — preliminary, not a size approval

The current exact package declarations are `@tesseract.js-data/eng@1.0.0`, `@tesseract.js-data/hin@1.0.0`, and `@tesseract.js-data/deu@1.0.0`; package metadata identifies the npm wrapper packages as MIT and points to `naptha/tessdata`. The upstream `naptha/tessdata` repository identifies its traineddata collection as Apache-2.0. These are separate notices: retain the MIT package-wrapper notice and include the Apache-2.0 traineddata license/attribution when redistributing the model bytes. The upstream repository documents `4.0.0_best_int` as its integerized `tessdata_best` model family, published to npm; this is not the separate `tessdata_fast` family.

The public UNPKG listing reports the English `4.0.0_best_int/eng.traineddata.gz` file as 2.95 MB (compressed). Its exact uncompressed size was not verified. Exact Hindi and German raw/gzip sizes, model hashes, generated `dist/ocr` footprint and full deployment artifact increase: **NOT VERIFIED**. A byte-level attempt through the GitHub file connector returned no decodable content for the binary traineddata; UNPKG/registry pages did not expose usable per-file sizes for Hindi/German in the available inspection. Do not ship Hindi or German in v1.4.0 until their actual files and sizes are measured from the installed package and generated deployment artifact. Do not claim a size or release approval based on estimates.
